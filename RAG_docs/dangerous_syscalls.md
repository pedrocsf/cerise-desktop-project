Fact Sheet: dangerous_syscalls
Script Objective

This detection focuses on monitoring the execution of high-risk and low-frequency Linux system calls (syscalls) that are typically not required by standard user-space applications. These syscalls provide deep interaction with the operating system kernel and other running processes, enabling advanced control, inspection, or modification of system behavior.

Examples include ptrace, mount, setns, and bpf, which can be abused to:

Inspect, manipulate, or inject code into other running processes.

Escape container or namespace isolation boundaries.

Modify filesystem views or mount malicious filesystems.

Load, attach, or execute eBPF programs that can intercept system calls, network traffic, or kernel events.

While these syscalls are legitimate and necessary for certain low-level tools, debuggers, container runtimes, and observability platforms, their appearance in unexpected contexts is a strong signal of suspicious or malicious activity. The goal of this script is to surface anomalous syscall usage that deviates from the expected behavior of the calling process.

Anomaly Patterns

An application-level process (such as a web server, API service, background worker, or database engine) invoking ptrace to attach to or trace another process, especially one owned by a different user or running with higher privileges.

Invocation of the mount syscall by a process that is not part of the system initialization, container runtime, or a known administrative utility, particularly when executed by an unprivileged or sandboxed process.

Use of setns to join or manipulate Linux namespaces (PID, mount, network, or user namespaces) by a process that is not expected to manage containers or isolation boundaries.

Execution of the bpf syscall by binaries that are not recognized as system observability agents, networking components, or performance monitoring tools.

Repeated or automated attempts to call these syscalls, which may indicate probing behavior or exploitation attempts.

Syscall usage originating from unusual execution paths, such as temporary directories, writable locations, or recently dropped binaries.

Normal Patterns (Common False Positives)

Debugging and development tools such as gdb, strace, ltrace, or language-specific debuggers legitimately using ptrace to inspect or control target processes during troubleshooting.

Container runtimes, orchestration agents, and system management scripts (e.g., Docker, containerd, CRI-O, systemd) using mount and setns as part of normal container lifecycle management.

Observability, networking, or security agents (such as performance profilers, tracing frameworks, or CNI plugins) using the bpf syscall to load and manage eBPF programs.

System startup scripts or maintenance tasks running with elevated privileges that perform namespace or mount operations as part of expected system configuration.

Vendor-supplied agents that may bundle advanced kernel interactions as part of legitimate functionality, particularly in cloud or enterprise environments.

Base Criticality Level

4 (High) – The improper or unexpected use of these syscalls is a strong indicator of potentially malicious behavior. These capabilities are commonly leveraged during post-exploitation phases, including privilege escalation, container escape, lateral movement, stealthy persistence, and kernel-level monitoring or tampering. Even a single occurrence can be significant if the calling process context is suspicious.

Suggested Correlation

Any alert generated by this detection should be promptly investigated, with special attention to contextual correlation. Priority should be elevated if correlated with:

privilege_escalation events, such as abnormal changes in user IDs, capabilities, or sudo usage.

kernel_module_load or other kernel modification activities.

Execution of unknown or unsigned binaries shortly before or after the syscall.

File system anomalies, such as mounts from unexpected sources or changes in namespace mappings.

Network or process injection indicators suggesting deeper system compromise.

When combined with additional behavioral signals, alerts related to dangerous syscalls can provide high-confidence detection of advanced attacks or misuse of powerful kernel interfaces.
